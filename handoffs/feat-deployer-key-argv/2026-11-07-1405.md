## Decisions and gotchas
- Reported, not fixed: on this machine `~/.aws` is a symlink to `/mnt/c/Users/tay09/.aws`, a 9p
  drvfs mount with no `metadata` option. The real `credentials` and `config` files show mode 777,
  so 0600 cannot hold there. The AWS CLI writes the file either way, and this change does not affect
  it. Fixing it means WSL mount settings or moving the files, which is outside this script. Only the
  modes were read, not the contents.
- An existing credentials file with a loose mode keeps it: `import` leaves 0644 as 0644 and the CLI
  prints a warning. `aws configure set` also left it at 0644, so this is not a regression. A new
  file is created 0600.
- `import` chosen over writing the section from a builtin: the CLI keeps owning the file format,
  comments and other profiles, and `AWS_SHARED_CREDENTIALS_FILE` works with no code here. Checked on
  aws-cli 2.35.6. The cost is that the secret sits in the 0600 temp file for about as long as the
  import takes.
- Known limit, also true of the old script: a signal between `create-access-key` and the end of the
  import orphans the key with no recovery message. SIGKILL also leaves the temp file behind, because
  no trap can run. A rerun would issue a second key, and IAM allows 2 per user.
- A failed `create-access-key` now leaves `region` and `output` in the config with no key. That is
  harmless: the early exit checks only `aws_access_key_id`, which returned non-zero for a config-only
  profile, and `import` into such a profile worked. A full rerun after that failure was not run.
- Do not add HUP, INT and TERM traps. I added them after a failing check, then removed them. The
  failure was the check waiting on a subshell's pid, not the script's. A minimal repro showed bash
  runs the EXIT trap on all three signals.
- Not run against real AWS, as the brief requires, so the real `create-access-key` text output was
  not exercised. That `read` line and its query are unchanged.
- The check is not in the repo, because the brief limits the change to this one script. It lives in
  this session's scratchpad, so it will not outlive the session. Its design is described above.
