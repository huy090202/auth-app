# Analysis: ~/.aws on drvfs, mode 777 (2026-11-07)

Read-only analysis. Nothing on the machine was changed and no credential value was read. Profile
names came from `aws configure list-profiles`.

## Findings
- `~/.aws` is a symlink to `/mnt/c/Users/tay09/.aws`. `credentials` and `config` show mode 777. The
  mount has no `metadata` option, and `/etc/wsl.conf` has no `[automount]` section.
- Linux home is ext4 and mode 700, but the symlink target sits outside it, so the 700 does not
  protect these files.
- Six profiles are in scope: `default`, `poc-deployer`, `alpha-deployer`, `hub-deployer`,
  `auth-gate-deployer`, `auth-app-deployer`. This affects more than auth-app.
- Linux accounts: only `root` and `ongdev2k2` have a login shell. Services run as `etcd` and
  `messagebus`, and mode 777 lets those accounts read the file. Not tested by running as them.
- Windows ACL on the folder and on `credentials`: SYSTEM, Administrators and `MSI\PC` only. No
  `Users` or `Everyone`, so other non-admin Windows accounts are not granted access.
- No sign of Windows tools using the folder: `where.exe aws sam terraform` found nothing, the
  default AWS CLI paths are empty, there is no AWS Toolkit in the Windows VS Code extensions folder,
  and the folder holds only `config` and `credentials`, no `sso`, `cli` or `sam` cache. This lowers
  the risk of moving; it does not prove nothing reads the folder.
- Repository scripts only use the CLI and `AWS_PROFILE`. None hard-codes this path as a dependency.
- No evidence of exposure.

## Limits of a fix
Mode 600 stops other Linux accounts. It does not stop a process running as `ongdev2k2`, a Windows
administrator, or Windows access through `\\wsl$`. The larger remaining risk is long-lived keys on
disk, above all `default` if it is an admin key, which was not checked.

## Options
1. Move to the Linux filesystem: recommended. Small, reversible, needs no restart, and affects no
   other mount.
2. `metadata` under `[automount]`: rejected. Needs `wsl --shutdown` and changes all Windows mounts.
3. Environment variables to a Linux copy: rejected. Leaves two copies, and the old one is still open.
4. Accept: rejected. Six keys, reachable by service accounts, and the fix is cheap.

## Proposed steps (not run; each needs the human's go-ahead)
1. Confirm nothing on Windows uses the folder, such as Docker Desktop or other tools.
2. Replace the symlink with a real `~/.aws` (700) and copy both files in at mode 600. Copy, do not
   move, so the Windows folder remains as the rollback.
3. Check with `aws configure list-profiles`, and `aws configure list --profile <name>` for each.
4. Run one harmless real call per profile in use, such as `aws sts get-caller-identity`.
5. After a few days, delete the Windows copy. Until then it is still a readable copy of the keys.

Rollback before step 5: remove the new directory and recreate the symlink.

## Repository
No branch needed: this is a machine matter. The row can close as `abandoned` with a note once the
human has decided. Separately, consider replacing `default` if it is a long-lived admin key.

## Decision and impact check (2026-11-07)
- The human confirmed AWS is only installed and run in WSL, and approved option 1. The commands are
  given to the human to run. Not run yet.
- Impact on other projects' deploys: none expected. The AWS CLI resolves `~/.aws` on each call, and
  no project was found depending on the Windows path.
  - `/home/work` scan, excluding build output, dependency folders and `.git`: the Windows path
    appears only in these handoffs; `AWS_SHARED_CREDENTIALS_FILE` and `AWS_CONFIG_FILE` only in
    these handoffs; `~/.aws` only in a comment in the two `00-deployer.sh` copies.
  - Shell startup files, the user crontab and user systemd units have no AWS reference.
  - `config` holds only `region` and `output`, and `credentials` only key id and secret, for six
    profiles (key names read, not values). No SSO, role or `credential_process` paths to break.
  - Not scanned: anything outside `/home/work`. CI systems use their own secrets.
- Whether `default` is an admin key is still unknown: the human confirmed it is the default profile,
  not its permissions.

## Move done (2026-11-07)
- The human ran steps 1 to 3. `~/.aws` is a real directory on ext4, mode 700, with `config` and
  `credentials` at mode 600. All six profiles resolve to the same ARNs before and after, by
  `aws sts get-caller-identity`, which proves the keys work. No deploy was run.
- Remaining: delete the Windows copy `/mnt/c/Users/tay09/.aws` after a few days of normal deploys,
  since it still holds all six keys. `default` is the IAM user `huy`; its policies and key age have
  not been reported.

## `default` profile (2026-11-07)
- IAM user `huy`, with `AdministratorAccess` attached directly and no groups. One active access key,
  created 2026-06-17 (143 days old). The folder's last change is about 3 minutes after that, so the
  key has probably sat in the 777 location since it was created.
- Recommendation: rotate it now, as routine hygiene, since there is no evidence of compromise.
  Consider SSO later.
- Rotation commands were given to the human, not run. They use `aws configure import`, checked in a
  sandbox with fake keys on aws-cli 2.35.6: it overwrites the existing `default` keys, keeps
  `region` and `output`, leaves other profiles alone, and the file stays 600.
